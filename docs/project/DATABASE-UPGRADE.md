# 数据库升级、备份与恢复

KTVS-056 将数据库保护纳入 Server 与 Desktop 的启动顺序：检查待应用迁移 → 对既有 SQLite 数据库创建一致性备份 → `PRAGMA integrity_check` → 执行 EF Core 迁移 → 播放状态恢复 → 启动服务。

只有存在待应用迁移且 `station.db` 已存在时才备份；普通启动不会制造重复备份。备份保存在数据库同目录的 `backups` 子目录，命名为 `station-before-migration-<UTC>-<唯一值>.db`，成功升级后也保留供人工回退。

若迁移抛出异常，程序关闭数据库连接并用 SQLite 在线备份 API 将迁移前快照恢复到原数据库，再执行完整性检查，最后以稳定的升级异常终止启动。恢复过程不删除数据库，不创建空库替代，也不触碰媒体文件。原始迁移异常作为内部异常保留，公开界面不得暴露路径。

## 人工恢复

1. 退出 Station，确认没有 Desktop/Server 进程使用数据库。
2. 复制当前 `station.db` 到单独的故障取证位置，不要删除它。
3. 选择升级前备份，在副本上执行 `PRAGMA integrity_check` 并确认返回 `ok`。
4. 优先使用已验证的上一版本 Station 和备份副本恢复；不要通过清空 `data` 或重建索引替代恢复。
5. 恢复后核对歌曲、收藏、历史、房间队列和人工音轨映射，再重新尝试升级。

自动测试注入了“删除歌曲后抛错”的破坏性迁移替身，确认服务从一致性备份恢复原歌曲；所有文件均位于随机临时测试目录。真实正式库升级前仍需另行复制备份并执行实机演练。
